The clusters that do the work are described entirely as Cluster API objects in the management
cluster. Nothing about them is installed by hand.

## Hosted control plane

A workload cluster's control plane is a `K0smotronControlPlane`: k0s controllers and their
datastore running as pods in the management cluster, exposed to the nodes through a Service.

- **Cheap and isolated.** A control plane costs a few hundred MiB and no VM. Each cluster has
  its own.
- **Independent versions.** The workload cluster's Kubernetes version and API feature gates are
  set in its own spec, separately from the management cluster. Clusters run the latest minor
  (1.37); Agent Substrate, for example, needs 1.36+ and certificate feature gates.
- **Managed like the model managed-Kubernetes services use**: the provider runs the control
  plane, the customer sees nodes.

## Node pools

Each node pool is a `MachineDeployment` whose machines are `CloudHypervisorMachine`s, so each
node is a VM that banlieue creates on a host. The pools in the reference design:

| Pool | Nodes | Runs |
|---|---|---|
| `gpu` | VMs with a GPU passed through; tainted so only GPU work lands there | GPU Operator, inference servers |
| `cpu` | Plain VMs | Agent Substrate, its datastore and object storage, cluster add-ons |

What a node pool gives you:

- **Replacement:** delete a `Machine` (or let a `MachineHealthCheck` do it) and a new VM joins.
- **Rolling upgrades:** change the machine template (a new node image, more memory) and the
  pool rolls node by node.
- **Scale to zero:** `replicas: 0` on the GPU pool releases the GPU and its pinned memory when
  nobody's using it.
- **Spread:** machines can be placed across hosts (failure domains).

## As many workload clusters as you need

A workload cluster is just a set of objects in the management cluster: a `Cluster`, its
`K0smotronControlPlane`, and one `MachineDeployment` per node pool. Another cluster is the same
objects under another name. Control planes are pods, so each extra cluster costs a few hundred
MiB, not a VM, and they all share the same hosts.

That makes the cluster boundary a design choice rather than a capacity one.

<ArchitectureFlow client:visible name="clusters" />

Common topologies:

| Topology | Clusters | When |
|---|---|---|
| **Combined** | one cluster with `gpu` and `cpu` pools | Small footprint, one team. The example deployment starts here. |
| **Inference split out** | an **inference** cluster (GPU pools only) and an **agents** cluster (CPU pools, Agent Substrate) | GPUs are shared by several consumers, or the inference platform has its own upgrade cadence, Kubernetes version, scheduler (Kueue, KAI, DRA) and on-call. Agents call inference across clusters through the egress gateway. |
| **Per tenant or environment** | one cluster per team, customer or stage, each with its own pools | Hard isolation of control planes, RBAC and upgrades; a shared inference cluster can serve them all. |
| **Per GPU class** | one inference cluster per GPU type or generation | Different drivers, node images or sharing modes per hardware generation. |

What changes between them is only *what calls what across a cluster boundary*: an agents
cluster reaches an inference cluster through an exposed, authenticated inference endpoint
(Gateway API, mTLS or a token added by the egress gateway) instead of a cluster-local Service.
The management plane, the hosts and the GitOps flow stay the same. Each cluster gets its own
`clusters/<name>/` path in the repository and its own Flux.

The reference design is written as one combined cluster because that's what one host runs
today; splitting inference out is the first step when there's a second GPU host.

## In the repository

Each workload cluster is a directory under `workload-clusters/` and one Flux Kustomization in
`clusters/homelab/workload-clusters.yaml`. The first, `ai-01`, is the combined topology:

| File | Objects |
|---|---|
| `cluster.yaml` | `Cluster`, `K0smotronControlPlane` (k0s 1.37, kine on SQLite, NodePort on the management node) |
| `pool-cpu.yaml` | `CloudHypervisorMachineTemplate`, `K0sWorkerConfigTemplate`, `MachineDeployment` |
| `health-cpu.yaml` | `MachineHealthCheck`: a node that stays `NotReady` (or never appears) is replaced |
| `addons.yaml` | Flux `Kustomization`s that apply `cluster-addons/` *into* ai-01 (GPU Operator) |

How a node joins, end to end:

1. The `MachineDeployment` creates a `Machine`, a `K0sWorkerConfig` and a
   `CloudHypervisorMachine` from the templates.
2. k0smotron renders the worker's join configuration as cloud-config into a bootstrap
   `Secret`, and Cluster API names it on the `Machine`.
3. banlieue's controller checks that the `Secret` really is that `Machine`'s bootstrap data and
   copies it into the `CloudHypervisorMachine`'s user data (`BootstrapDataReady`).
4. The host's provider boots the VM only then; cloud-init installs k0s and joins the hosted
   control plane through its NodePort.

### Add-ons: hub and spoke

Cluster API keeps each workload cluster's admin kubeconfig as a `Secret` (`<cluster>-kubeconfig`)
in the management cluster. A Flux `Kustomization` with `spec.kubeConfig` pointing at it applies
manifests *into* that cluster, so workload clusters run no Flux of their own: one repository,
one Flux and one signed artifact drive every cluster, and an add-on's rollout to a cluster is a
reviewed change to that cluster's `addons.yaml`. At a larger scale the alternative is Flux in
each cluster (Flux Operator can install it there); the trade is fewer moving parts against
not depending on the management cluster to keep reconciling.

Templates are treated as immutable: a change is a new template (`-v2`) and the
`MachineDeployment` rolls to it.

The objects live in `banlieue-system` because a Cloud Hypervisor host serves only its own
`Provider`'s namespace, and a host's `Provider` lives in banlieue's install namespace. The hosted
control plane's pods therefore run there too; they need root, so the namespace's Pod Security is
lowered from `restricted` to `privileged` enforcement, with `restricted` warnings and audit kept on.
That's a deliberate trade-off until banlieue supports hosts' Providers in their own namespaces. The [roadmap](../../reference/roadmap/) has what's next: the `gpu` pool.
