## Title

Smoother installs on Ubuntu and libvirt-free Cloud Hypervisor hosts (no default behaviour change)

## Description

I brought up a management cluster with `bootstrap-k0s-cluster.sh` (one
Cloud Hypervisor node, Ubuntu 24.04 cloud image) and a host with
`banlieue host cloud-hypervisor install`, on an **Ubuntu 24.04** host with
**no libvirt installed**, then installed banlieue alongside Cluster API
v1.14 with Flux. Everything worked in the end. These are the four places
where I had to stop and dig, each fixed here as an opt-in or docs-only
change.

**Principle for all four: nothing changes on the tested path** (Debian 13,
libvirt present, Debian cloud images, no Cluster API). Defaults stay the
same; the new behaviour only applies where the old one failed.

Environment: Ubuntu 24.04.5, kernel 6.8, systemd 255, banlieue v0.5.7,
cloud-hypervisor v53.0, k0s v1.35.10, Cluster API v1.14.4, k0smotron v2.3.1.

### 1. docs: use `providers.banlieue.io` wherever Cluster API may be installed

**Pitfall.** Cluster API's `core-components.yaml` defines its own namespaced
`Provider` kind (`providers.clusterctl.cluster.x-k8s.io`, clusterctl's
inventory). Once CAPI is installed, which ADR-0096 supports, `kubectl get
provider <name>` resolves to clusterctl's kind and returns NotFound for a
banlieue Provider that exists. A script of mine waited forever on exactly
that.

**Change.** Docs only. Replace `kubectl get provider(s)` with
`kubectl get providers.banlieue.io` (or the existing short name `prov`) in:

| File | Occurrences |
|---|---|
| docs/src/guides/cloud-hypervisor-host.md | 5 |
| docs/src/guides/capacity-scheduling.md | 4 |
| docs/src/guides/vsphere-provider.md | 4 |
| docs/src/guides/libvirt-provider.md | 2 |
| docs/src/guides/observability.md | 2 |
| docs/src/guides/provider-lifecycle.md | 2 |
| docs/src/guides/proxmox-provider.md | 1 |
| docs/src/developer/local-development.md | 1 |
| scripts/check-infra-identifiers-test.sh | 1 (check whether it's test data before touching) |

Plus a short note in `guides/cluster-api.md`: "Cluster API also defines a
`Provider` kind; use `providers.banlieue.io` (or `prov`) with kubectl."

Commit: `docs: name banlieue Providers unambiguously next to Cluster API`

### 2. bootstrap: accept SHA-256 pins and `SHA256SUMS` for cloud images

**Pitfall.** `verify_cloud_image` only knows SHA-512 (`CLOUD_IMAGE_SHA512`,
or `SHA512SUMS` beside the image), which fits Debian. Ubuntu's cloud images
publish only `SHA256SUMS`, so `LIBVIRT_IMAGE_KIND=cloud` with an Ubuntu
image fails with "no checksum available". The only ways out are to compute a
SHA-512 yourself or to set `IMAGE_VERIFY=off`. Also, Ubuntu's `SHA256SUMS`
lines are `<digest> *<file>` (binary-mode marker), which the current
`$2 == f` match wouldn't find even if it looked there.

**Change.** Opt-in, precedence keeps today's behaviour first:

1. `CLOUD_IMAGE_SHA512` (unchanged, still wins)
2. new `CLOUD_IMAGE_SHA256`
3. `auto`: `SHA512SUMS` (unchanged), and **only if that yields nothing**,
   `SHA256SUMS`, accepting the `*` marker

`verify_digest` already handles `sha256`. Sketch (bash 3.2 safe, no `${x^^}`):

```bash
CLOUD_IMAGE_SHA256="${CLOUD_IMAGE_SHA256:-}"

verify_cloud_image() {
  [[ "$IMAGE_VERIFY" == "off" ]] && { log "IMAGE_VERIFY=off -- skipping cloud image verification"; return 0; }
  local base algo="" expected="" pair sums
  base="$(basename "$CLOUD_IMAGE_URL")"
  if [[ -n "$CLOUD_IMAGE_SHA512" ]]; then
    algo=sha512; expected="$CLOUD_IMAGE_SHA512"
  elif [[ -n "$CLOUD_IMAGE_SHA256" ]]; then
    algo=sha256; expected="$CLOUD_IMAGE_SHA256"
  elif [[ -z "$BASE_IMAGE_PATH" ]]; then
    for pair in "sha512 SHA512SUMS" "sha256 SHA256SUMS"; do
      set -- $pair; algo="$1"; sums="$2"
      log "Fetching $sums for $base"
      expected="$(curl -fsSL "$(dirname "$CLOUD_IMAGE_URL")/$sums" 2>/dev/null \
                  | awk -v f="$base" '{ n = $2; sub(/^\*/, "", n) } n == f { print $1; exit }' || true)"
      [[ -n "$expected" ]] && break
    done
  fi
  [[ -n "$expected" ]] || { log "no checksum available -- set CLOUD_IMAGE_SHA512, CLOUD_IMAGE_SHA256 or IMAGE_VERIFY=off"; exit 1; }
  verify_digest "$CLOUD_IMAGE" "$algo" "$expected"
}
```

Also: the IMAGE_VERIFY comment block mentions `CLOUD_IMAGE_SHA256`, and the
`--print-env-template` output (a vSphere env file) names both cloud image
pins in a commented-out block marked libvirt-backend only, so sourcing it
sets neither; `bootstrap-k0s-cluster-test.sh` gains cases for
(a) SHA-256 pin, (b) a `SHA256SUMS` with `*` markers, and (c) SHA512SUMS
still preferred when both exist.

Commit: `feat(bootstrap): verify cloud images against SHA-256 pins and SHA256SUMS`

### 3. bootstrap: don't default the image pool into libvirt's tree when there is no libvirt

**Pitfall.** Since ADR-0099 Decision 5, Cloud Hypervisor is the default VMM,
so a host needs no libvirt. But `POOL_DIR` still comes from
`virsh pool-dumpxml default`, falling back to
`/var/lib/libvirt/images/k0s-bootstrap`, and line ~439 creates it
**unprivileged** (`mkdir -p "$POOL_DIR"`) at top level. On a host without
libvirt that fails with a bare `Permission denied` before any step runs (the
same symptom the comment above `_default_pool_dir` describes for a moved
pool). I set `POOL_DIR`/`CH_VM_DIR` up front, so this comes from reading the
code. Reproduce on a libvirt-free host with
`env -u POOL_DIR -u CH_VM_DIR ./scripts/bootstrap-k0s-cluster.sh vms`.

**Change.** Unchanged whenever `virsh` reports a default pool. Only when
`virsh` is absent (or reports none) **and no node uses the libvirt VMM**:

- fall back to `/var/lib/k0s-bootstrap/images` (so `CH_VM_DIR` becomes
  `/var/lib/k0s-bootstrap/k0s-ch`, whose parents the CH VM user can search);
- create `POOL_DIR` with `sudo install -d -o "$USER"` when the user can't,
  since the CH path already requires sudo;
- otherwise fail with a message that names `POOL_DIR` and `CH_VM_DIR`.

(If the maintainers prefer, the minimal version of this is the last bullet
alone: the clear error message.)

Commit: `fix(bootstrap): default the image pool off libvirt on Cloud Hypervisor-only hosts`

### 4. docs: Ubuntu hosts need an AppArmor rule for swtpm

**Pitfall.** Ubuntu ships `/etc/apparmor.d/usr.bin.swtpm`, which confines
`swtpm` to libvirt's paths. `banlieue host cloud-hypervisor install` then
fails at the EK CA stage:

```
Error: (as banlieue) swtpm_setup --tpm2 --tpmstate /var/lib/banlieue/.host-scratch --create-ek-cert ... failed (exit status: 1): /usr/bin/swtpm exit with status 256
```

and the kernel log has:

```
apparmor="DENIED" operation="mknod" class="file" profile="swtpm" name="/var/lib/banlieue/.host-scratch/.lock" comm="swtpm" requested_mask="c" denied_mask="c"
```

**Change.** Docs only: an "Ubuntu (AppArmor)" note under Requirements in
`guides/cloud-hypervisor-host.md`. The packaged profile already includes
`local/usr.bin.swtpm`, so no packaged file is edited. That local file may
already hold the administrator's own rules, so the rules are appended (each
only if absent, so re-running is safe), never written over it:

```sh
f=/etc/apparmor.d/local/usr.bin.swtpm
for rule in '/var/lib/banlieue/** rwk,' '/run/banlieue/** rwk,'; do
  sudo grep -qxF "$rule" "$f" 2>/dev/null || echo "$rule" | sudo tee -a "$f" >/dev/null
done
sudo apparmor_parser -r /etc/apparmor.d/usr.bin.swtpm
```

With it, install, EK CA and `selftest` (which manufactures a vTPM) pass.
I haven't exercised guest vTPMs with it (my nodes run `CH_TPM=false`), so
the rule may need the storage-class paths too. Having `preflight` detect
this, or `install` write the rule, changes what install does to the host,
so I'd raise that separately as an issue rather than put it in this PR.

Commit: `docs(cloud-hypervisor): AppArmor rule for swtpm on Ubuntu hosts`
